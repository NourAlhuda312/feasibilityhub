# FeasibilityHub — Final MVP

FeasibilityHub is a focused course workspace for **Business Feasibility Study** classes. It replaces the shared idea spreadsheet with student accounts, self-formed teams, professor review, semester separation, course-scoped roles, course codes, invitation links, and Excel/CSV export.

> Start with [`START_HERE.md`](./START_HERE.md). The current ZIP is intentionally ready for UI/flow review **before** connecting the real Supabase database.

## Product decisions in this final MVP

### Sign in does **not** ask “Professor or Student?”
This is intentional. A person has one account, while their role belongs to each course membership.

Example:

| User | Fall 2026 — BFS-301 | Spring 2027 — ENT-410 |
|---|---|---|
| Ahmad | Student | Assistant |
| Dr. Lina | Professor | Professor |
| Maya | Admin | Student |

After sign-in, `/dashboard` reads the user’s course memberships and opens the correct workspace. Inside a course, clicking the FeasibilityHub logo returns to that course’s relevant dashboard rather than the public home page.

### Professors create courses; students join courses
A faculty-enabled account can create a course and select its academic semester. Every course receives a unique join code such as `BFS30-7KQ9M2`.

Students can join using either:
- the **course code** from their signed-in dashboard, or
- a **shareable course invitation link** generated by Professor/Admin.

A user cannot make themselves a professor by choosing a role at sign-in. Course creation is separately authorized using `profiles.can_create_courses` or the server-only bootstrap allowlist `PLATFORM_ADMIN_EMAILS`.

## Student experience

- Email/password account with email confirmation
- Join a course by course code or invitation link
- Create a group and automatically become its initial leader
- Maximum 3 students per group
- One group per student per course
- Leader can add an existing enrolled classmate by email
- Leader can generate/share a private group invitation link
- Leader can transfer leadership to another current member
- Leader can remove a non-leader member
- Group leader submits the business idea
- Idea name + quick description
- Revision history after requested changes
- Clear workflow state: Draft / Submitted / In review / Changes requested / Approved

## Professor / staff experience

- Course operations dashboard
- Submission pipeline and review queue
- “Start review” explicitly locks student editing
- Approve or request changes with feedback
- Academic semester attached to every course
- Course-scoped Professor / Admin / Assistant / Student roles
- Professor/Admin can add existing accounts as Professor, Admin, or Assistant
- Generate student course invitation links
- Export CSV and XLSX

## Review-lock workflow

```text
Draft
  ↓ student leader submits
Submitted
  ↓ staff clicks “Start review”
In review  ← student editing is LOCKED
  ├─ Approve → Approved (locked)
  └─ Request changes → Changes requested (leader may edit again)
                         ↓ resubmit revision
                      Submitted
```

The lock is not only visual. The database migration also blocks new idea revisions when the idea is `in_review` or `approved`.

## Group workflow

```text
Student A joins course
  ↓
Creates group → becomes Leader
  ├─ Add Student B by email
  │    (B must already have joined the course)
  └─ Generate invite link → share with Student B/C

Maximum = 3 students

Leader can later:
  ├─ Transfer leadership to B or C
  └─ Remove a non-leader member
```

If a classmate has not created/joined the course yet, the leader shares the group invite link rather than directly adding them.

## Interactive Preview Mode

Preview Mode works without Supabase and persists demo state in browser `localStorage`, so the main workflow can be tested before database setup.

Open:
- `/preview/professor`
- `/preview/student`

### Recommended end-to-end preview test

1. Open `/preview/professor`.
2. Find **CoCompass** and click **Start review**.
3. Open `/preview/student` and then **Business Idea**.
4. CoCompass should show **In review** and editing should be locked.
5. Return to the professor review page and choose **Request changes** with feedback.
6. Return to the student idea page; editing should be available again.
7. Resubmit; the revision number increments and status becomes **Submitted**.
8. Start review again and approve it.
9. Verify the student sees **Approved** and the idea is locked.

Preview routes also include:
- `/preview/student/group` — add demo members, share invite, transfer leader, remove member
- `/preview/student/idea` — revision/edit-lock workflow
- `/preview/professor/groups`
- `/preview/professor/ideas`
- `/preview/professor/team`
- `/preview/professor/settings`

The preview export endpoints generate real demo CSV/XLSX files without a database.

## Data model

```text
profiles
  └─ can_create_courses   (platform/faculty capability only)

academic_semesters
        │
      courses ── join_code
        │
        ├── course_memberships ── profiles
        │      role = professor/admin/assistant/student
        ├── course_invites
        │
```

## Security design

### Row Level Security
All application tables in the exposed `public` schema have RLS enabled. Students are scoped to their own course/group data; staff permissions are derived from the requested course membership.

### Privileged server operations
Multi-step actions use a server-only Supabase admin client only **after** the action authenticates the user and verifies their course role. Never expose `SUPABASE_SECRET_KEY` to the browser.

### Authorization data
Course roles live in `course_memberships`, not user-editable auth metadata and not a role selected at sign-in.

### Invitation tokens
Raw invitation tokens are returned only when generated. The database stores their SHA-256 hash.

### Database constraints
The migration enforces key invariants including:
- max 3 students per group,
- one group per student per course,
- unique group numbers per course,
- unique course join codes,
- idea revisions blocked during `in_review` and `approved`.

## Known MVP boundaries

Intentionally deferred until after the first real-course MVP:
- grades/rubrics,
- PDF/report uploads,
- market-feasibility chapter forms,
- financial modeling,
- email notifications beyond authentication,
- course archive UI,
- detailed staff removal/ownership-transfer UI,
- hosted end-to-end automated tests.

The schema is deliberately prepared for later chapter modules attached to the same `group_id` rather than rebuilding identity/group/course data.
